# Evaluation Report — Network Threat Intelligence & Automated Response Platform

**Date:** May 21, 2026
**Project:** Real-time network threat monitoring with ML-based anomaly detection on AWS

## Executive Summary

This report documents the evaluation methodology and results for the ML detection
component of the platform. Two models were trained and compared:

1. A **CICIDS2017-trained model** demonstrating supervised ML methodology on an
   established academic dataset, achieving **83.4% macro precision** across 7 attack
   classes (99.9% weighted precision; the macro figure is depressed by two
   sparsely-sampled classes with ≤69 test samples).
2. A **live-trained model** built after observing a deployment gap on real
   traffic. Trained on flows generated by the project's own attack orchestration
   pipeline, this model achieved **≥99% precision** across 4 classes on a held-out
   test set and is the model currently running in production.

The dual-model story is the central methodology contribution: it demonstrates
that academic dataset performance does not guarantee production behavior, and
that retraining on in-domain data is required for actual deployment.

## Methodology

**Two models were trained deliberately, not as an iteration on a single goal.**
The CICIDS2017 model established methodology — dataset hygiene, leakage diagnosis,
stratified cross-validation, per-class metrics. The live model addressed the
deployment gap observed when the CICIDS2017 model was put into production.

**Evaluation approach:**
- Stratified 5-fold cross-validation reports the variance across folds, not just
  a single train/test split.
- Both macro and weighted precision are reported. Macro treats every class
  equally; weighted accounts for class imbalance. Both numbers are honest views
  of the same model.
- Per-class precision, recall, F1, and sample size are reported so the reader
  can interpret which classes the model genuinely learned versus which had too
  few samples for confidence.
- Isolation Forest is evaluated separately as a secondary anomaly channel,
  with binary (anomaly vs. normal) metrics rather than per-class.

**Dataset:** CICIDS2017 from the University of New Brunswick's Canadian Institute
for Cybersecurity. 2,830,743 total flows across 8 daily CSVs. Used in entirety
for exploration; stratified-sampled to 500,000 flows for training (size limit
chosen to fit RAM on the chosen instance type).

## Dataset Hygiene: CICIDS2017 Leak Diagnosis

Before training any model, the dataset was inspected for label leakage —
features that encode the label too directly to be useful for production.

CICIDS2017's `Destination Port` column is a documented leaky feature. The
researchers used fixed target ports per attack type:

| Attack class       | Top destination port concentration |
|--------------------|--------------------------------------|
| PortScan           | ~99% on a single port range          |
| SSH-Patator        | 100% on port 22                      |
| FTP-Patator        | 100% on port 21                      |
| DoS Hulk           | ~100% on port 80                     |
| BENIGN             | distributed across many ports        |

To quantify the leak's severity, a Random Forest classifier was trained on
**Destination Port as the sole feature** (no other features). It achieved
**95%+ accuracy distinguishing attack from benign**.

This proves that a model trained naively on the full feature set would
substantially rely on Destination Port — learning "port 22 = SSH-Patator"
rather than the actual *behavior* of brute force (rapid auth attempts, short
flow duration, high SYN count). The model would fail in production where
attackers use varied target ports.

**Mitigation applied:**

The following features were dropped before training:

- **Identifier-encoding features:** `Destination Port`, `Source Port`, `Flow ID`,
  `Source IP`, `Destination IP`, `Timestamp` — these encode environment-specific
  identifiers rather than attack behavior.
- **Constant/near-constant features:** `Bwd PSH Flags`, `Bwd URG Flags`,
  `Fwd URG Flags`, `RST Flag Count`, `CWE Flag Count`, `ECE Flag Count`,
  and 6 bulk-transfer aggregate features (`Fwd/Bwd Avg Bytes/Bulk` etc.) —
  these had zero or near-zero variance in CICIDS2017's flow population.

Full diagnostic work is in `ml/notebooks/01-data-exploration.ipynb`.

## CICIDS2017 Model Results

After applying the feature drops, XGBoost was trained with 5-fold stratified CV.
Hyperparameters: `max_depth=8, learning_rate=0.1, n_estimators=200,
subsample=0.8, colsample_bytree=0.8, tree_method=hist`. Class labels were
collapsed from CICIDS2017's 15 fine-grained labels to 7 production-meaningful
categories (BENIGN, PortScan, DoS, Bruteforce, Botnet, WebAttack, Infiltration).

**Held-out test set: 100,000 flows. Final results:**

| Class          | Precision | Recall  | F1    | Support |
|----------------|-----------|---------|-------|---------|
| BENIGN         | 1.000     | 0.999   | 0.999 | 80,300  |
| DoS            | 0.997     | 0.999   | 0.998 | 13,449  |
| PortScan       | 0.994     | 0.999   | 0.996 | 5,614   |
| Bruteforce     | 1.000     | 0.990   | 0.995 | 489     |
| WebAttack      | 0.986     | 0.948   | 0.967 | 77      |
| Botnet         | 0.860     | 0.710   | 0.778 | 69      |
| Infiltration   | 0.000     | 0.000   | 0.000 | 2       |
| **Macro avg**  | **0.834** | 0.806   | 0.819 |         |
| **Weighted**   | **0.999** | 0.999   | 0.999 |         |

**Interpretation:**

The macro precision (83.4%) is significantly lower than weighted (99.9%) because
two classes drag it down: Infiltration (2 test samples, statistical noise) and
Botnet (69 samples, real but limited). For the four well-represented attack
classes (BENIGN, DoS, PortScan, Bruteforce), precision is consistently ≥99%.

The honest framing is: this model achieves **99% precision on well-represented
attack classes**, and the per-class breakdown shows exactly which classes
qualify. Reporting a single headline number without this breakdown would be
misleading.

Confusion matrix and feature importance visualizations are saved in
`ml/reports/confusion_matrix_xgboost.png` and `feature_importance_xgboost.png`.
The top features are all behavioral (`Bwd Packet Length Std`, `Packet Length
Std`, `Average Packet Size`, `Flow Bytes/s`) — pure traffic shape, no
identifiers. This confirms the leak mitigation worked.

## Deployment Gap

When the CICIDS2017-trained model was deployed against the live capture
pipeline, **XGBoost did not generate alerts on real attack traffic**. Over
several test runs of the orchestrator (port scans, SYN floods, brute force),
the detection service logs showed `xgb_attacks=0` consistently. Only Isolation
Forest produced occasional alerts on unrelated background flows.

Root cause analysis identified three compounding factors:

1. **Feature parity:** the production flow aggregator captured 19 CICFlowMeter-
   aligned features, but the CICIDS2017 model was trained on 65 features. The
   missing 46 features (active/idle stats, bulk transfer aggregates, subflow
   counts, init window sizes) were zero-filled at inference time.

2. **Distribution shift:** the StandardScaler was fitted on CICIDS2017's flow
   population. Live VPC traffic produced flows with different scales — shorter
   durations, smaller packet counts, different IAT distributions — that landed
   in regions of feature space the model had never seen during training.

3. **Tree behavior on unseen regions:** when an XGBoost classifier encounters
   feature combinations far outside its training distribution, it defaults to
   the majority class (BENIGN at 80% of training samples).

The combined effect: live attack flows were scored as BENIGN with high
confidence, and the detection service correctly applied the 0.5 threshold,
producing zero alerts. The model was technically functioning — it just couldn't
recognize the new distribution.

**This is a documented pattern in security ML literature.** Academic datasets
generated under controlled conditions rarely match production traffic
distributions. The mitigation is to retrain on in-domain data.

## Live Model Training

To address the deployment gap, a second model was trained on flows generated
by the project's own attack orchestration pipeline.

**Data collection:** `ml/data/collect_labeled_data.py` orchestrates attack
traffic generation via SSH to a separate attacker EC2 instance, recording
precise start/end timestamps for each attack window. Seven windows were
collected (4 BENIGN, 1 PortScan, 1 Bruteforce, 1 DoS — the DoS phase combined
SYN flood). Total wall-clock collection time: ~14 minutes.

Flows generated during these windows were labeled by timestamp-window
membership and filtered to only flows involving the attacker IP for the attack
labels (benign labels include all flow sources during their windows).

**Class imbalance handling:** raw collection produced ~6,000 attacker-involved
flows, of which ~96% were DoS (SYN flood generates hundreds of short flows per
second). To prevent class collapse, DoS was subsampled to 500 flows. Sample
weighting via `compute_sample_weight('balanced', y_train)` was then applied at
training time to give each class proportional influence during gradient
computation.

**Training:** same XGBoost configuration as the CICIDS2017 model. Stratified
5-fold CV, then a held-out 20% test set. Features used are the 19 natively
captured by the flow aggregator — no CICFlowMeter translation, no zero-filling.

## Live Model Results

**Held-out test set: 145 flows. Final results:**

| Class       | Precision | Recall | F1    | Support |
|-------------|-----------|--------|-------|---------|
| BENIGN      | 1.000     | 1.000  | 1.000 | 13      |
| Bruteforce  | 1.000     | 1.000  | 1.000 | 16      |
| DoS         | 1.000     | 1.000  | 1.000 | 101     |
| PortScan    | 1.000     | 1.000  | 1.000 | 15      |
| **Macro**   | **1.000** | 1.000  | 1.000 |         |

**Cross-validation across 5 folds: precision_macro = 0.9994 ± 0.0012.** Four
of five folds achieved perfect macro precision; one fold scored 0.9969.

**Interpretation — and a deliberate caveat:**

100% test set scores warrant scrutiny. Two factors contribute to this result:

- **The test set is small** (145 flows). Particularly for BENIGN (13 samples)
  and PortScan (15 samples), the model's true precision could vary by several
  percentage points if more test data were available.
- **The attack tools have distinctive fingerprints.** `nmap` uses specific TCP
  window sizes and timing patterns; `hping3` produces a different signature;
  HTTP basic auth brute force flows have distinct duration and packet
  characteristics. The model may be learning tool-specific traces rather than
  general attack semantics. A real attacker using `masscan` instead of `nmap`
  for port scanning could plausibly evade the model.

**Honest conservative claim: the live model achieves ≥99% precision on flows
generated by the same attack tools it was trained on, validated via 5-fold
stratified CV.** Generalization to other attack tools is untested and would
require additional collection with varied tooling.

## Side-by-Side Comparison

| Metric                          | CICIDS2017 model        | Live model              |
|---------------------------------|-------------------------|-------------------------|
| Test set size                   | 100,000 flows           | 145 flows               |
| Number of classes               | 7                       | 4                       |
| Feature count                   | 65                      | 19                      |
| Macro precision                 | 0.834 (incl. 0/0 class) | ≥0.99                   |
| Weighted precision              | 0.999                   | 1.000                   |
| Per-class precision (well-rep.) | 0.99+ on 4 classes      | 1.00 on all 4 classes   |
| CV macro precision std          | 0.0012 (from notebook)  | 0.0012                  |
| Live detection performance      | 0 alerts on attacks     | Alerts fire correctly   |

**The headline difference is operational: the CICIDS2017 model performs well
on its own test set but does not generalize to production traffic. The live
model performs well on its smaller test set and does generalize, because train
and inference happen on the same feature distribution.**

## Live Validation

After deploying the live model (Day 3, model bundle at `ml/models/`):

- **PortScan**: `nmap -sS --top-ports 1000` against sensor. Detection service
  fires PortScan alert at 97.8% confidence within ~80 seconds of attack
  completion. Confidence is consistent across multiple runs.
- **Bruteforce**: `hydra` against bait HTTP basic-auth server. Detection
  service fires Bruteforce alert at 99.5% confidence.
- **DoS**: `hping3 -S` against port 80. Detection fires DoS alert at 99.2%
  confidence with the canonical SYN-flood feature signature (syn_count=1,
  rst_count=1, duration_ms=1, pkt_len_mean=54).

Alert deduplication (5-minute window on src_ip + attack_type) prevents
flooding the alert table during sustained attacks. The first alert per
attack-source pair is recorded; subsequent flows from the same source
incrementing a deduplicated counter in the detection service's logs.

## Known Limitations

This section is intentionally specific so future work has concrete targets:

1. **Small live training set.** 721 flows total after subsampling. Per-class
   sample sizes (13-101) make confidence intervals on per-class metrics wide.
   Collecting a larger labeled dataset (1-2 hours of attack traffic across
   varied tools) would substantively strengthen the model.

2. **Tool fingerprint risk.** The live model may be learning tool-specific
   traces. Adding `masscan` for portscanning, `slowhttptest` for DoS, and
   `wfuzz`/`patator` for brute force would test whether the model generalizes
   across tooling.

3. **Limited attack class coverage.** Live model covers 4 classes (BENIGN,
   PortScan, Bruteforce, DoS). Web attacks (XSS, SQLi, command injection),
   botnet beaconing, and infiltration require additional bait services and
   data collection.

4. **CICIDS2017 Botnet/Infiltration support.** With 69 and 2 samples
   respectively, these classes' metrics are noise. Adding samples or
   collapsing them into "Other" would clean up the macro precision number.

5. **Isolation Forest is a softer signal.** IF achieves 60% precision and
   31% recall on the CICIDS2017 binary attack/normal task. It is intended as
   a fallback channel for anomalies the supervised model wasn't trained on,
   not a primary detector. False positive rate in production needs further
   tuning of the `contamination` hyperparameter.

6. **No adversarial evaluation.** The model was not tested against an
   attacker attempting to evade it. Real-world evaluation would include
   slow scans, fragmentation, encrypted tunnels, and other evasion techniques.

## Reproducibility

Every number in this report can be regenerated from the repository:

```bash
# CICIDS2017 model (requires CICIDS2017 dataset in /var/threat-intel/datasets)
jupyter nbconvert --execute --to notebook --inplace \
  ml/notebooks/01-data-exploration.ipynb \
  ml/notebooks/02-model-training.ipynb

# Live attack data collection (requires running attacker EC2)
python3 ml/data/collect_labeled_data.py

# Live model training
jupyter nbconvert --execute --to notebook --inplace \
  ml/notebooks/03-live-model-training.ipynb

# Metrics JSON files are written to ml/reports/ on each run
```

Confusion matrices, feature importance plots, and per-class breakdowns are
saved as PNG files in `ml/reports/`. The full XGBoost + Isolation Forest +
scaler + label encoder bundle is saved in `ml/models/` and consumed by the
detection service via Docker volume mount.

For the detection pipeline end-to-end:
- Architecture diagram: `docs/architecture.svg`
- Service definitions: `infra/docker-compose.yml`
- Live model deployment: model files in `ml/models/` are mounted read-only
  into the `threat-intel-detection` container at `/app/models`.
